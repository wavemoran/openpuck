# Browser installer

The installer is a static site in `installer/`. It uses the Web Serial API and
a vendored copy of Espressif's [esptool-js](https://github.com/espressif/esptool-js)
to back up, install and restore a puck from the browser. There is no build step,
no npm package and no external request at runtime. For owners, see
[install.md](install.md).

URLs: `https://wavemoran.github.io/openpuck/` (install) and
`https://wavemoran.github.io/openpuck/restore.html` (restore).

## Supported browsers

- Firefox 159 or newer, any desktop OS.
- Chrome or Edge on Windows, Linux and ChromeOS.
- Not Chrome, Edge or other Chromium browsers on macOS (see
  [Browser behavior](#browser-behavior-it-relies-on-and-works-around)).
- Not Safari, phones or tablets.

`js/support.js` (`checkSupport`) decides this from the user agent, platform and
whether `navigator.serial` exists, and returns the message the page shows.

Windows and Linux are expected to work but have not been tested on hardware yet.
See [roadmap.md](roadmap.md).

## Layout

```
installer/
  index.html, restore.html   one step per screen
  css/style.css
  js/constants.js       USB ids, registers, sizes, expected flash ID
  js/md5.js, hash.js    MD5 (for the stub's digests) and SHA-256 (crypto.subtle)
  js/transport.js       RobustTransport (extends esptool-js Transport)
  js/flashio.js         readFlashVerified, writeImagesVerified
  js/device.js          openLoader, prepareFlash, holdPower, button helpers,
                        resetToApp, waitForPuck, safeDisconnect
  js/images.js          backup check, partition table parsing, install plan,
                        backup file name, manifest parsing
  js/support.js         checkSupport()
  js/flow.js            connectPuck, runInstall, runRestore
  js/app.js, restore-app.js   DOM wiring only, no protocol logic
  vendor/esptool-js/    bundle.js, LICENSE, README.md
  test/*.test.js        node:test tests
  firmware/             generated by tools/installer_site.py, not committed
```

## How it works

### Flow

`flow.js` holds the whole sequence. All I/O (loader, ports, timers, downloads,
UI) is injected, so the tests drive it with mocks. The UI interface is
`ui.show(step, details)`, `ui.progress(done, total, label)`,
`ui.cue("hold" | "release" | "done" | "error")`,
`ui.saveBackup(fileName, bytes, sha256Hex)` and `ui.confirmBackupSaved()`.

`runInstall`:

1. Fetch `firmware/manifest.json` and every part from the same origin. Check
   size and SHA-256. Stop on any mismatch, before touching the puck.
2. The user clicks Connect; the UI calls `requestPort` with the `303a:1001`
   filter.
3. `connectPuck(port)` (below).
4. `prepareFlash`: load the stub, attach, check the flash ID is `0x164020`,
   read the MAC.
5. Read the full 4 MB (progress), then `checkBackup` (size, `0xE9` at 0,
   `0xAA 0x50` at 0x8000). Stop without writing if it fails.
6. `ui.saveBackup`, then wait for `ui.confirmBackupSaved()`. Nothing is written
   before this resolves.
7. `planInstall`, write and verify, `resetToApp`, `safeDisconnect`, done.

`runRestore` checks the file with `checkBackup`, connects the same way, writes
all 4 MiB at 0, verifies, and resets to the app.

`connectPuck` mirrors `tools/flash.py`. It opens the loader and tries
`detectChip("default_reset")`.

- If that works, the puck was running OpenPuck (it holds the power latch through
  the reset). Hold the latch (`holdPower`); if the button reads pressed, cue
  "release" and wait for it to be let go.
- If it fails, the original software let the puck switch off. Disconnect, cue
  "hold", and wait for the `connect` event of a `303a:1001` port (up to 10
  minutes, cancelable). Wait 2 s, open the new port, `holdPower`, cue
  "release", wait for the button release (30 s timeout), wait 0.5 s.

Errors before any write reset the puck to the app and offer Try again. After
writing has started the page does not reset: it says not to unplug, offers Try
again (the remaining plan on the same connection if it is still open) and points
to the restore page.

### Install plan

`planInstall` follows `flash.py cmd_flash`:

- Write the bootloader (0x0), partition table (0x8000) and app (0x10000) as
  separate images. The merged image pads 0x9000-0xFFFF with `0xFF`, which would
  erase saved settings on every update.
- Compare `backup[0x8000:0x8C00]` with the new table's first 0xC00 bytes. If
  they differ, the layout changed, so also write `0xFF` over every data
  partition of the new table (it compresses to almost nothing). If they match,
  settings are kept.
- Each write is verified with `loader.flashMd5sum(addr, len)` against our own
  MD5. The MD5 command is retried up to 3 times before a mismatch is real.

### RobustTransport and the verified read

esptool-js 0.7.0 `readFlash` is unusable here: it keeps 1024 packets in flight,
concatenates quadratically and never consumes the trailing 16-byte MD5 packet.
`flashio.js` implements `readFlashVerified` using the stub's `READ_FLASH`
(0xD2) command, as Python esptool does:

- Payload `<IIII`: address, length, packet size 0x1000, max in flight.
- The stub sends SLIP frames of up to 0x1000 bytes. After each frame the host
  sends a SLIP frame with the u32le total received so far.
- After the data the stub sends one 16-byte frame, the MD5 of the data. The
  host compares it with its own.

The read runs in chunks (default 0x10000, 16 in flight). A dropped byte, a
timeout (5 s per packet) or a digest mismatch retries that chunk (up to 10
times). Recovery acknowledges the full length and drains input
(`drainInput(500, 4000)`) before the retry. It takes an `AbortSignal`.

`RobustTransport` (`transport.js`) extends the esptool-js `Transport` with what
the verified read needs, including timeouts, `drainInput` and abort support.

### Reset to the app

esptool-js `loader.after("hard_reset")` never raises RTS in 0.7.0, so
`resetToApp` does it directly on the transport: `setDTR(false)`,
`setRTS(true)`, 200 ms, `setRTS(false)`, 200 ms. This boots the app. OpenPuck
then holds the latch and starts by itself.

## Browser behavior it relies on and works around

- **Hard reset.** See above. Fixed in our code, not by patching the vendored
  file.
- **`readFlash`.** See above.
- **Buffer size.** Chrome needs the port opened with `bufferSize: 1048576`. The
  default of 255 bytes overflows.
- **Chrome on macOS loses `0xFF` runs.** Its serial layer marks parity and
  framing errors in-band (PARMRK), which corrupts runs of `0xFF` and raises
  `BreakError`. Flash contains many such runs, so a backup would be incomplete.
  The verified read fails safely, but the page also refuses this combination up
  front. Firefox on a Mac is fine. A fix would need a small helper uploaded to
  the puck that avoids sending raw `0xFF` runs (see [roadmap.md](roadmap.md)).
- **`port.open()` does not reset the chip.** The reset comes from esptool-js
  `detectChip("default_reset")`, which uses its USB-JTAG sequence and works.
- **Port reuse after re-enumeration.** After the puck re-enumerates, a granted
  port can be reopened without a user gesture. Listen for the `connect` event on
  `navigator.serial` and use `event.target`: Chrome gives a new `SerialPort`,
  Firefox the same one. `getPorts()` is empty on a first visit. The listener
  exists only while the flow is waiting for the puck and is removed afterward;
  an always-on listener that connects would trap the puck in download mode.
- **No `disconnect` event on chip reset.** The port stays open from the
  browser's point of view, so the flow does not wait for one. `safeDisconnect`
  closes with a timeout.
- **Secure context.** Web Serial needs HTTPS. `localhost` counts as secure, so
  the local server below works over plain HTTP.

## Tests

```sh
tools/test-installer.sh
```

Needs Node 22 or newer. It runs the `node:test` suites in `installer/test/` with
coverage and fails under 90% line coverage of `installer/js/` (the DOM wiring in
`app.js` and `restore-app.js` is excluded). The tests mock the serial port and
the loader. They cover MD5 against `node:crypto`, SLIP decoding across random
chunk splits, `readFlashVerified` against a simulated stub (clean, dropped bytes,
digest mismatch, retries exhausted, abort), `images.js` edge cases, the
`support.js` user agent matrix, and `flow.js` for the OpenPuck path, the
original-software path, nothing written before the backup is confirmed, erasing
when the table differs, and errors before and after writing.

## Trying it locally

```sh
idf.py build
python3 tools/installer_site.py --build-dir build --version dev
python3 -m http.server -d build-installer 8000
```

Then open <http://localhost:8000/> in a supported browser. `installer_site.py`
copies `installer/` (without `test/`) to `build-installer/`, and writes
`firmware/manifest.json` plus the three images with their sizes and SHA-256
values. It can also take a release's parts zip:
`--parts-zip openpuck-0.1.0-parts.zip --version 0.1.0`.

Use a puck you have a backup of. The page does real writes.

## Updating the vendored esptool-js

The files are in `installer/vendor/esptool-js/`. See
`installer/vendor/esptool-js/README.md` for the version, where it comes from,
the checksums and how to verify them. Keep `bundle.js` unmodified. After an
update, rerun the tests and check the workarounds above still apply (hard reset,
`readFlash`).
